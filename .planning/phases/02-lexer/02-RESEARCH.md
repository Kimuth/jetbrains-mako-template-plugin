## Summary

Phase 2 builds a JFlex-generated lexer that is the sole artifact for this phase (no parser, no PSI yet). The lexer's job is to assign every byte in a `.mako` file a named `IElementType` token without gaps or overlaps, and to support incremental re-lexing by encoding its full context in a single integer state. This is the foundation Phase 3 (parser) and Phase 4 (highlighting) depend on.

The IntelliJ Platform expects lexers to be generated by JFlex using the `idea-flex.skeleton` (bundled by the Gradle GrammarKit plugin) and wrapped in a thin `FlexAdapter` subclass. The `ParserDefinition` is also created in this phase — it wires the lexer to the language and is required before the IDE will invoke the lexer at all. However, since the parser (Phase 3) is not built yet, `createParser()` returns a stub and the PSI tree is minimal.

Mako's syntax has five distinct lexical regions that need separate JFlex states: (1) template text (HTML/plain content), (2) `${...}` expression blocks, (3) `%` control lines, (4) `<%tag ... %>` block tags and code blocks, and (5) comment forms (`##` and `<%doc>`). The critical design challenge is the filter expression `${x | h,trim}` — the `|` inside a `${...}` must be tokenized as `FILTER_SEP`, not as Python bitwise OR. This is solved by context: the `|` token type is only assigned inside the EXPRESSION JFlex state, not in YYINITIAL.

The incremental re-lex requirement (PARS-03) is satisfied naturally by JFlex when the state machine has predictable restart points — specifically, Mako constructs all terminate before the end of a line or at explicit closing delimiters (`}`, `%>`, `</%tag>`), so the lexer returns to `YYINITIAL` (state 0) frequently, giving the platform many restart anchors.

**Primary recommendation:** Write `MakoLexer.flex` with five named states (`EXPRESSION`, `TAG_ATTRS`, `CODE_BLOCK`, `COMMENT_LINE`, `DOC_COMMENT`), define all token types as `IElementType` constants in a `MakoTokenTypes` Kotlin object, wrap the generated class in `MakoLexerAdapter extends FlexAdapter`, create a stub `MakoParserDefinition` registered in `plugin.xml`, and activate the commented-out `generateMakoLexer` Gradle task that already exists in `build.gradle.kts`.

### Pattern 1: JFlex Header for IntelliJ Template Language

**What:** Every JFlex file targeting IntelliJ must have this exact header to work with `FlexAdapter` and `idea-flex.skeleton`.

**Example:**
```java
// Source: https://plugins.jetbrains.com/docs/intellij/lexer-and-parser-definition.html
// and intellij-rust/intellij-toml TomlLexer.flex
package com.github.kimuth.jetbrainsmakotemplateplugin.lang;

import com.intellij.lexer.FlexLexer;
import com.intellij.psi.tree.IElementType;
import static com.github.kimuth.jetbrainsmakotemplateplugin.lang.MakoTokenTypes.*;
import com.intellij.psi.TokenType;

%%

%class _MakoLexer
%implements FlexLexer
%unicode
%function advance
%type IElementType
%eof{  return;
%eof}

// Custom constructor required by FlexAdapter
%{
  public _MakoLexer() {
    this((java.io.Reader)null);
  }
%}
```

**Why `%function advance`:** The `FlexAdapter` calls `advance()` (not `yylex()`) — this directive renames the scanner method to match.

**Why `%type IElementType`:** The scanner method returns `IElementType` tokens, not integers.

### Pattern 2: Mako Lexer States and Token Types

**What:** The complete state design for handling all Mako constructs.

**States needed:**
```
%state EXPRESSION       // Inside ${ ... } — tracks brace depth
%state TAG_ATTRS        // Inside <% tag attributes ... %> or <% code %>
%state CODE_BLOCK       // Inside <% python code %> body
%state MODULE_BLOCK     // Inside <%! module code %>
%state DOC_COMMENT      // Inside <%doc> ... </%doc>
```

**Token types (MakoTokenTypes.kt):**
```kotlin
// Source: IntelliJ Platform SDK — IElementType usage pattern
// https://plugins.jetbrains.com/docs/intellij/implementing-lexer.html

    @JvmField val MODULE_CONTENT = IElementType("MODULE_CONTENT",MakoLanguage) // Python code inside <%! %>
```

### Pattern 3: Critical State Transitions in MakoLexer.flex

**What:** The YYINITIAL state detects all Mako construct openings and delegates to sub-states. Sub-states return to YYINITIAL on closing delimiters.

**Key rules (pseudo-JFlex):**
```
<YYINITIAL> {
  "${"           { yybegin(EXPRESSION); return EXPR_START; }
  "##" [^\n]*    { return LINE_COMMENT; }
  "<%doc>"       { yybegin(DOC_COMMENT); return DOC_OPEN; }
  "<%!" / [^-]   { yybegin(MODULE_BLOCK); return MODULE_OPEN; }
  "<%" / [a-z]   { yybegin(TAG_ATTRS); return TAG_OPEN; }     // <%def, <%block etc.
  "<%" / [ \t\n] { yybegin(CODE_BLOCK); return CODE_OPEN; }   // inline code block
  "</" "%"       { /* end tag -- handled in TAG_ATTRS state */ }
  "%%"           { return TEMPLATE_TEXT; }   // escaped %
  "%" / [a-z ]   { return CONTROL_LINE; }    // control line (must be at line start)
  [^]            { return TEMPLATE_TEXT; }   // everything else is template text
}

<EXPRESSION> {
  "}"            { yybegin(YYINITIAL); return EXPR_END; }
  "|"            { return FILTER_SEP; }      // ONLY inside EXPRESSION — key disambiguation
  [a-zA-Z_][a-zA-Z0-9_]*  { return EXPR_CONTENT; }
  .              { return EXPR_CONTENT; }
}

<DOC_COMMENT> {
  "</%doc>"      { yybegin(YYINITIAL); return DOC_CLOSE; }
  [^]            { return DOC_CONTENT; }
}

<CODE_BLOCK> {
  "%>"           { yybegin(YYINITIAL); return CODE_CLOSE; }
  [^]            { return CODE_CONTENT; }
}
```

**Note on `%` control lines:** Mako's actual rule is that `%` must be the first non-whitespace character on a line. A pure JFlex lookahead like `"%" / [a-z ]` is insufficient because JFlex `^` anchors match line starts at the character level. The correct approach is to track whether the lexer is at a line start position (either via JFlex's `%` line-start condition or by emitting newlines as separate tokens and checking state). The Mako reference lexer (`mako/lexer.py`) uses a multiline regex with `(?<=^)` lookbehind. In JFlex, the `^` anchor works in rules and is the correct tool: `^[ \t]*"%"`(excluding `%%`).

### Anti-Patterns to Avoid

- **Activating `generateMakoParser` in Phase 2:** The `.bnf` file does not exist. Activating `GenerateParserTask` without a `.bnf` file causes a Gradle build failure. Leave `generateMakoParser` commented until Phase 3.
- **Returning `null` from `advance()` mid-file:** JFlex lexers must cover every character. Any unmatched input causes a `null` return, which IntelliJ treats as a fatal lexer error. Always include a fallback rule `[^] { return TokenType.BAD_CHARACTER; }`.
- **Using `[^\r\n]*` for line-spanning tokens without accounting for Windows line endings:** Mako files may use `\r\n`. Use `[^\n]*` and handle `\r` as whitespace, or use `{LineTerminator}` macros.
- **Encoding `%` control line detection without the `^` JFlex anchor:** `%` is only a control line when it is the first non-whitespace character on a line. Without `^[ \t]*"%"` the lexer will tokenize `${ "a%" | h }` incorrectly.
- **Naming the generated class `MakoLexer` (no underscore):** JFlex generates a class with the exact `%class` name. Convention is `_MakoLexer` (underscore prefix) so the generated Java class is clearly distinct from the hand-written `MakoLexerAdapter` Kotlin class.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Lexer DFA generation | Manual state machine in Kotlin | JFlex `.flex` file + `GenerateLexerTask` | JFlex generates an optimized DFA; hand-rolled state machines have exponential edge-case failure modes |
| CharSequence compatibility | Custom `CharSequence`-to-`char[]` bridge | `idea-flex.skeleton` via `--charat` (automatic with GrammarKit plugin) | Without `--charat`, the JFlex output is incompatible with IntelliJ's incremental lexing architecture |
| Token type registry | `enum` or `String` constants | `IElementType` instances with `MakoLanguage` | Platform APIs (`TokenSet`, `ParserDefinition`, `SyntaxHighlighter`) all operate on `IElementType` references — enums don't satisfy the interface |
| Incremental re-lex wiring | Custom `Lexer.start()` override tracking | `FlexAdapter.start()` calling `reset()` on generated class | `FlexAdapter` delegates to the JFlex skeleton's `reset(buffer, start, end, state)` which correctly repositions the scanner — any custom version risks off-by-one errors |
| Whitespace token constant | Custom `IElementType("WHITESPACE", ...)` | `TokenType.WHITE_SPACE` | If you create a custom whitespace token, `getWhitespaceTokens()` won't match it and whitespace will appear as errors in the PSI tree |

**Key insight:** The GrammarKit + JFlex pipeline is a complete, battle-tested system. The only hand-written code needed is the thin `FlexAdapter` wrapper, the `IElementType` constants, and the `ParserDefinition`. Everything else is generated or platform-provided.

## Common Pitfalls

### Pitfall 1: The `|` Filter Separator vs. Python Bitwise OR

**What goes wrong:** If `|` is tokenized as a generic `PIPE` in all contexts, then `${a | b}` cannot be distinguished from `${a|b}` (bitwise OR). Phase 4 syntax highlighting and Phase 3 parser both depend on this being correct.

**Why it happens:** `|` is a valid Python operator. A context-free lexer cannot determine whether it is Mako filter syntax or Python operator syntax.

**How to avoid:** Use a dedicated JFlex `EXPRESSION` state. In `YYINITIAL`, `|` is never a valid token start so it falls through to `TEMPLATE_TEXT`. In `EXPRESSION` state, after a complete primary expression, `|` is `FILTER_SEP`. The lexer's job is tokenization, not expression parsing — so the simplest correct approach is: within `EXPRESSION` state, the first `|` not inside a nested `()`, `[]`, or string literal is always `FILTER_SEP`. This matches Mako's grammar: `${expr | filter_list}` where `expr` cannot itself contain an unbalanced `|` at the top level.

**Warning signs:** `${x | h}` highlights `h` as a Python identifier instead of a filter name; `${a | b}` tokenizes `b` as a filter name when it should be an expression operand.

**Practical JFlex rule (inside EXPRESSION state):**
```
"|" / [^|]    { return FILTER_SEP; }   // single | not followed by | (Python || is rare in templates)
"||"          { return EXPR_CONTENT; } // Python boolean OR stays as expression content
```

### Pitfall 2: Nested Brace Handling in `${...}` Expressions

**What goes wrong:** `${{'key': 'value'}}` (a Python dict literal inside an expression) causes the lexer to close the expression on the first `}` it sees.

**Why it happens:** A simple `EXPRESSION` state rule `"}" → EXPR_END` fails for any expression containing a nested dict, set, or lambda with braces.

**How to avoid:** Track brace depth in the JFlex `%{ %}` user code section:
```java
%{
  private int braceDepth = 0;
%}

<EXPRESSION> {
  "{"           { braceDepth++; return EXPR_CONTENT; }
  "}"           { if (braceDepth > 0) { braceDepth--; return EXPR_CONTENT; }
                  else { yybegin(YYINITIAL); return EXPR_END; } }
}
```

**Warning signs:** `${{'a':1}}` tokenizes only `{{'a':1}` as expression content and leaves trailing `}` as `BAD_CHARACTER`.

**Impact on PARS-02:** The requirement for "correctly handles nested constructs" specifically requires brace depth tracking.

### Pitfall 3: Lexer State Integer Must Cover All State

**What goes wrong:** After editing a line mid-file, syntax highlighting jumps to the wrong state because the integer returned from `getState()` doesn't uniquely identify the lexer's full context.

**Why it happens:** JFlex's `yystate()` returns only the current state integer (0 = `YYINITIAL`, 1 = `EXPRESSION`, etc.). If brace depth is tracked in a Java field, that field is not included in the state integer. When IntelliJ restarts lexing at a restart point, it passes the saved integer back but doesn't restore the field.

**How to avoid:** For Mako, brace depth inside `${...}` only changes within a single expression (depth resets to 0 at `EXPR_END`). The lexer returns to `YYINITIAL` at the end of every top-level Mako construct. IntelliJ restarts at positions where `getState() == 0` (YYINITIAL), so the brace depth field is irrelevant at restart points (it is always 0 at YYINITIAL). Verify this holds; if any construct can span multiple lines with non-zero brace depth persisting, the state integer must encode that depth (e.g., `state | (braceDepth << 4)`).

**For Mako specifically:** `${...}` expressions rarely span multiple lines in templates, but `<% %>` code blocks can. The `CODE_BLOCK` state has no nested delimiters to track — it runs until `%>` regardless. So brace depth is only non-zero inside `EXPRESSION`, and `EXPRESSION` never crosses a line boundary in practice (Mako expressions are typically single-line). Low risk, but verify.

**Warning signs:** Token colors on lines below an edit "shift" or stay wrong after editing — classic sign of a state restart problem. Test with `LexerTestCase.checkCorrectRestartOnEveryToken()`.

### Pitfall 4: `generateMakoLexer` Task Not Wired Before `compileKotlin`

**What goes wrong:** Build fails with `ClassNotFoundException: _MakoLexer` or `Cannot access class '_MakoLexer'` because the generated Java file doesn't exist when Kotlin compilation begins.

**Why it happens:** Gradle task ordering is not implicit. Without `compileKotlin { dependsOn(generateMakoLexer) }`, Gradle may compile Kotlin before running JFlex generation.

**How to avoid:** Always add the `dependsOn` relationship. The existing commented-out stub in `build.gradle.kts` already has this — just uncomment it.

**Warning signs:** Clean build fails; incremental build succeeds (because `src/main/gen` was populated by a prior build).

### Pitfall 5: Empty Token Match Returns `null`

**What goes wrong:** Certain lexer rules can match empty strings in some JFlex versions (e.g., `[^]*` in a state where nothing matches). An empty match causes `advance()` to return `null`, which IntelliJ interprets as end-of-file.

**Why it happens:** JFlex rules like `[^]` at end-of-file, or rules where the matched text is empty, return `null` from `advance()`. IntelliJ stops highlighting at that point.

**How to avoid:** Always test with files ending in different characters. Add `%eof{ return; %eof}` to handle EOF gracefully. Use the Handlebars plugin pattern of checking for empty tokens and skipping them.

**Warning signs:** Syntax highlighting stops partway through a file with no apparent reason; the affected position varies based on file content.

### Pitfall 6: `%%` Escaped Percent Not Handled

**What goes wrong:** `%%` at the start of a line is Mako's escape for a literal `%`. If the lexer rule for `^"%" ...` doesn't check for `%%`, the first `%` of `%%` triggers a `CONTROL_LINE` and the second `%` is left as orphaned `TEMPLATE_TEXT`.

**Why it happens:** A naive `^[\ \t]*"%"` rule matches the first `%` of `%%`.

**How to avoid:** Add a rule before the control line rule: `^[\ \t]*"%%"  { return TEMPLATE_TEXT; }`. JFlex applies rules in order and uses longest match — `%%` is longer than `%`, so the `%%` rule wins if both match.

### Brace-Depth Counter in JFlex (PARS-02)

```java
    private int braceDepth = 0;

    private void resetBraceDepth() { braceDepth = 0; }
%}

// Inside <EXPRESSION> state rules:
<EXPRESSION> {
    "{"            { braceDepth++; return MakoTokenTypes.EXPR_CONTENT; }
    "}"            {
                     if (braceDepth > 0) {
                         braceDepth--;
                         return MakoTokenTypes.EXPR_CONTENT;

                         resetBraceDepth();
                         yybegin(YYINITIAL);
                         return MakoTokenTypes.EXPR_END;
                     }
                   }

    "||"           { return MakoTokenTypes.EXPR_CONTENT; }

    .              { return MakoTokenTypes.EXPR_CONTENT; }
```

## Complete Mako Token Coverage (PARS-01)

The following table maps every Mako construct from PARS-01 to the token type(s) used:

| Mako Construct | Token Type(s) | Notes |
|----------------|--------------|-------|
| `${expr}` | `EXPR_START`, `EXPR_CONTENT`, `EXPR_END` | `FILTER_SEP` + `FILTER_NAME` if filter present |
| `${expr \| h,trim}` | `EXPR_START`, `EXPR_CONTENT`, `FILTER_SEP`, `FILTER_NAME`, `EXPR_END` | Filter separator is only valid inside EXPRESSION state |
| `% for`, `% if`, `% while`, `% endif`, `% endfor` | `CONTROL_LINE` | Single token covering the whole line |
| `<%def name="foo">` | `TAG_OPEN` + `TAG_ATTR_*` tokens + `TAG_CLOSE` | TAG_OPEN includes the tag keyword |
| `</%def>` | `END_TAG` | Single token |
| `<%block>`, `<%inherit>`, `<%include>`, `<%namespace>`, `<%page>` | Same pattern as `<%def>` | |
| `<% code %>` | `CODE_OPEN`, `CODE_CONTENT`, `CODE_CLOSE` | Python inline code block |
| `<%! imports %>` | `MODULE_OPEN`, `MODULE_CONTENT`, `CODE_CLOSE` | Module-level Python block |
| `<%doc> text </%doc>` | `DOC_OPEN`, `DOC_CONTENT`, `DOC_CLOSE` | Multi-line comment |
| `## comment text` | `LINE_COMMENT` | Single token, includes `##` prefix |
| Template text (HTML etc.) | `TEMPLATE_TEXT` | Everything not matched by above |
| Unrecognized characters | `TokenType.BAD_CHARACTER` | Platform constant, never null |
| Whitespace only lines | `TokenType.WHITE_SPACE` | Platform constant |

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Manual `Lexer` subclass | JFlex + `FlexAdapter` | Stable since 2014 | JFlex approach is canonical; no reason to deviate |
| `GenerateLexer` task name | `GenerateLexerTask` task name | grammarkit 2023.x | Project already uses `GenerateLexerTask` in commented stub |
| `char[]` JFlex output | `CharSequence` via `--charat` and `idea-flex.skeleton` | Stable | GrammarKit plugin handles this automatically; no manual flag needed |
| `yylex()` method name | `advance()` via `%function advance` | Stable | Must use `%function advance` to match `FlexAdapter.advance()` call |
| Separate `FlexLexer` implementation | `FlexAdapter` subclass | Stable | `FlexAdapter` handles all the delegation; only the constructor is needed |

**Deprecated/outdated:**
- Using `%function yylex` and calling it manually: Do not use — `FlexAdapter` calls `advance()`, so the generated method must be named `advance`.
- ANTLR for IntelliJ lexers: ANTLR is an alternative but has no official GrammarKit Gradle support and is rarely used in IntelliJ plugins; JFlex is the standard.

## Open Questions

1. **Should `CONTROL_LINE` be a single token or split into keyword + body?**
   - What we know: For Phase 2 (lexer only), a single `CONTROL_LINE` token covering the entire `% keyword ...` line is sufficient for incremental re-lex and restart. Phase 3 (parser) will need to distinguish `% for` from `% endfor` from `% if`.
   - What's unclear: Whether Phase 4 syntax highlighting needs sub-tokens within control lines (e.g., highlight `for` differently from `endfor`), or whether a single `CONTROL_LINE` token and annotator-based highlighting suffices.
   - Recommendation: Use a single `CONTROL_LINE` token in Phase 2. If Phase 4 needs sub-tokens, the lexer can be revised in Phase 3/4 planning. This minimizes Phase 2 complexity.

2. **State integer overflow risk for deep nesting in CODE_BLOCK?**
   - What we know: `<% %>` code blocks can contain arbitrary Python code. Python code can contain `#` comments (not Mako `##`), string literals with `%>` inside, etc. The `CODE_BLOCK` state must handle `%>` appearing inside Python string literals.
   - What's unclear: Whether `<% code with "%>" in a string %>` is valid Mako (i.e., does the Mako parser itself use a stateful approach here?). Looking at `mako/lexer.py`, the regex for tag content uses `(?:'[^']*?'|"[^"]*?"|[^>])*` to skip string contents.
   - Recommendation: For Phase 2, implement a simple `CODE_BLOCK` state that returns `CODE_CONTENT` for everything until the first `%>`. This is incorrect for edge cases but correct for the vast majority of real Mako files. Document as a known limitation and address in Phase 3 if needed.

3. **Does the lexer phase need to distinguish specific tag names (`def`, `block`, `inherit`, etc.) as separate token types?**
   - What we know: PARS-01 lists all block tag types explicitly. Phase 3 (parser) needs to distinguish them for PSI node creation.
   - What's unclear: Whether the lexer should emit `TAG_OPEN_DEF`, `TAG_OPEN_BLOCK`, etc. (separate token types per tag) or a single `TAG_OPEN` with the tag name in the token text.
   - Recommendation: Use a single `TAG_OPEN` token type (with the full `<%def` text as the token text) in Phase 2. Phase 3 can either add specific token types or use text matching in the grammar. Simpler token set is better for Phase 2 — fewer token types = fewer states = easier to verify.

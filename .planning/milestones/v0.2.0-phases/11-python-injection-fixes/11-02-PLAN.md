<objective>
Fix the Python injection range for MakoExpression so filter names are excluded from
the injected Python fragment.

Purpose: When a Mako expression uses filters (e.g., ${x | h, trim}), the current
injector includes `| h, trim` in the Python range. This causes the Python language
service to see `x | h, trim` as Python code, which is invalid Python and triggers
false positives. The fix stops the injection range at the first FILTER_SEP token.

Output: Updated MakoPythonInjector.kt and MakoInjectionRangeTest.kt with range
boundary tests.
</objective>

    In the `is MakoExpression` branch of `getLanguagesToInject`, add logic to find
    the first FILTER_SEP child element and use its start offset as the injection end.

    Current code:
      val start = 2
      val end = nodeText.length - 1
      if (end > start) { ... }

    Replace with:

      val start = 2
      // Stop injection at the first FILTER_SEP child so filter names (e.g., h, trim in
      // ${x | h, trim}) are not presented to the Python language service as Python code.
      val filterSep = context.node.firstChildNode?.let { first ->
          var child = first
          var found: com.intellij.lang.ASTNode? = null
          while (found == null) {
              if (child.elementType == MakoTokenTypes.FILTER_SEP) found = child
              child = child.treeNext ?: break
          }
          found
      }
      // filterSep?.startOffset is document-absolute; subtract context.textRange.startOffset
      // to get offset relative to this host node.
      val end = if (filterSep != null) {
          filterSep.startOffset - context.textRange.startOffset
      } else {
          nodeText.length - 1
      }
      if (end > start) { ... }

    Keep all other branches (MakoCodeBlock, MakoModuleBlock) exactly as they are —
    those constructs do not have FILTER_SEP tokens so no change is needed.

    Add the required import at the top of the file if not present:

    (It may already be present via wildcard — check existing imports first.)
